# Market Reports — feasibility + architecture (2026-07-16)

Data-grounded (real parquet counts): can market readings scale state->county->city->neighborhood? Honest answer below.

## Verdict
County and state are genuinely, richly buildable NOW statewide: 90,676 closed sales in the trailing 12 months across 138 counties, with 129 clearing 25+ sales, so median sale price, median $/sqft, YoY, price distribution, and sold count can ship honestly for ~129 VA jurisdictions plus VA-state and DC. City/town works too but thins: 354 cities have 25+ sales (value metrics) and 246 have 50+ (safe for a $/sqft trend line). Neighborhood is the hard truth: subdivision exists ONLY in the tiny MLS pool (supplemental is 100% null), so after junk-filtering there are just 16 (county,subdivision) pairs with 10+ sales and 56 with 5+, essentially all in the NRV/Roanoke/SW-VA core. Heat/velocity metrics (sold-to-list, over-ask %, price-cut share, DOM, months-of-inventory, type mix) are computable ONLY on the MLS pool (0 rows of list price/DOM/active in supplemental), i.e. ~12 SW-VA counties, NOT statewide. The recommended system is ONE nightly-precomputed market_reports.parquet keyed by (level, geo_id), consumed by two additive read endpoints, that serves BOTH the in-app Market Reports tool and the programmatic SEO location pages from a single source of truth. Every metric carries its own {value, n, available} so pages degrade gracefully to a coverage-flagged or "not enough sales yet" state rather than fabricating readings, and thin/empty geographies feed a coverage waitlist that doubles as a demand signal and an email-capture SEO asset. Ship Phase 1 at STATE + COUNTY + CITY statewide (value tier) with heat behind a coverage flag; ship neighborhood as an explicitly-labeled SW-VA pilot only.

## Viability by level (measured)
- **STATE — broadly**: VA 85,783 + DC 4,893 closed sales trailing 12mo; sqft usable on 95.5% (86,634/90,693)
  - Two state roots only: /va and /dc. DC separates cleanly via county='District of Columbia'. Full value tier trivially. Heat tier only as a rolled-up NRV-footprint figure, flagged.
- **COUNTY — broadly**: 129 of 138 counties >=25 sales/12mo, 123 >=50, 108 >=100 (88,321 from supplemental + 2,372 MLS)
  - Primary Phase-1 geography. Value tier (median price, $/sqft, YoY, distribution, count) statewide. Heat tier only for the ~12 MLS-covered SW-VA counties, coverage-flagged; never render blank/zero heat elsewhere.
- **CITY — partial**: 844 cities in closed pool; 497 >=10, 354 >=25, 246 >=50
  - Gate value metrics at >=25 (354 cities ship); reserve $/sqft trend for >=50 (246). Below 25, roll the city up into its county page. Must nest under a county slug (city names scatter across counties in the raw feed).
- **NEIGHBORHOOD — thin**: subdivision 100% null in supplemental; after junk-filter only 16 (county,subd) pairs >=10 and 56 >=5, all NRV/Roanoke/SW-VA
  - NOT a statewide or programmatic feature. Ship as an explicitly-labeled SW-VA pilot of the ~16 (>=10) to ~56 (>=5) named neighborhoods, reusing build_markets.py's existing subdivision cards. Everywhere else the drill-down stops at city and shows 'neighborhood readings coming soon' + waitlist.

## Architecture
ONE precomputed, keyed dataset serves BOTH the in-app Market Reports tool AND the programmatic SEO location pages. Do not build two systems.

FLOW: nightly build -> data/market_reports.parquet -> warm-worker keyed lookup -> two additive /api/compbird/market endpoints -> Next.js App Router pages that render the SAME data whether shown inside /home (the tool) or at a public SEO URL.

1) ENGINE AGGREGATION (nightly precompute). New scripts/build_market_reports.py emits one row per (level, geo_id) for STATE / COUNTY / CITY / NEIGHBORHOOD. VALUE metrics (median sale price, median $/sqft, YoY, price-distribution histogram via FLOOR(price/bucket), sold count) come from BOTH pools UNIONed (supplemental_listings for statewide breadth + mls_lookup sold rows), computed statewide. HEAT/VELOCITY metrics (median + q25/q50/q75 DOM via QUANTILE_CONT, sold-to-list, %-over-ask, cut-share, months-of-inventory, active count, propertyTypeMix) come ONLY from mls_lookup and are stamped onto a geo ONLY where that pool covers it (NRV/SW-VA today). NEIGHBORHOOD rows are the existing scripts/build_markets.py subdivision cards folded in verbatim. A single-pass DuckDB GROUP BY over all counties measured ~0.01s, so this is a trivially cheap nightly job wired into tasks.py next to mls-rebuild-market-index, run after the hourly MLS refresh. All additive/compbird-only; zero change to Ratifyly engine output.

2) DATA SHAPE. market_reports.parquet keyed by (level, geo_id) with a parent geo_id pointer, so children-of lookups (counties in a state, cities in a county, neighborhoods in a county) are one indexed scan. Every metric carries {value, n, available}; per-geo coverage flags (heat / typeMix / neighborhoods) baked in.

3) SLUGS + TAXONOMY. Write a NEW url-slug normalizer; do NOT reuse cma_regions._norm_county (it collapses Roanoke City == Roanoke County -> 'roanoke' and mangles 'James City County' -> 'james'). Rules: lowercase, strip apostrophes/periods, non-alnum -> single hyphen, trailing descriptor -> controlled suffix (-county vs -city). Build the canonical jurisdiction universe from parcel_lookup.jurisdiction (86 values) + a small hand-maintained crosswalk: 39 VA independent cities (force -city + own node), an out-of-state denylist (NC/WV/'Out of Area'/null must be filtered, never published), DC = single node. Store slug<->canonical-display map so display stays 'Fiddler's Green, Blacksburg, Montgomery County, VA'. Cities nest as (county_slug, city_slug) resolved to the dominant county; never mint a bare /va/<city>.

4) APP ROUTES + RENDERING/SEO. One route tree under /home-values (public, SSG/ISR for SEO) that the in-app tool also links into (/home logged-in shell embeds the same server components). URL hierarchy: /home-values -> /home-values/va (+ /dc) -> /home-values/va/<county> -> /home-values/va/<county>/<city> -> /home-values/va/<county>/<neighborhood> (pilot only). Pages are Server Components fetching from the keyed endpoint at build/revalidate time (generateStaticParams over the qualifying geo list, ISR revalidate ~24h to match nightly build). This is the SEO destination from the utility roadmap and the in-app tool at once. Thin/empty geos render a 'not enough sales yet' state with a coverage-waitlist email capture (SEO-indexable, demand-signal). Design language = Aerial/Instrument (paper + electric-blue --cb-ember + mono figures).

ONE-SYSTEM DECISION: the tool and SEO pages differ only in chrome (auth shell + CTAs vs public header + JSON-LD), never in data or computation. Both consume MarketReading from the same parquet via the same endpoints.

## Wire contract
```
MarketReading JSON (one object per (level, geo_id); a SUPERSET of today's EngineMarket so the existing /markets landing cards keep working as a flattened projection):

{
  level: 'state' | 'county' | 'city' | 'neighborhood',
  geoId: string,            // the slug, e.g. 'va/montgomery-county/blacksburg'
  name: string,             // display, e.g. 'Blacksburg'
  area: string,             // full display path 'Blacksburg, Montgomery County, VA'
  state: 'VA' | 'DC',
  parent: string | null,    // parent geoId for drill-up
  generatedAt: string,      // ISO nightly build timestamp
  sold: {                   // VALUE tier, statewide
    n: number,
    medianPrice: number,
    medianPpsf: number,
    ppsfYoyPct: number | null,        // null when either 12mo window has n<25
    ppsfTrend: number[],              // sparkline; only when supported (city>=50, county w/ market_index history)
    distribution: { bucketLo: number, count: number }[]
  },
  velocity?: {              // HEAT tier, MLS-only geos
    medianDom: number,
    domQuantiles: { q25: number, q50: number, q75: number },
    monthsOfInventory: number,
    activeCount: number,
    soldToList: number,
    pctOverAsk: number,
    cutShare: number,
    heat: number
  },
  typeMix?: { label: string, count: number }[],   // MLS-only
  available: { velocity: boolean, typeMix: boolean, neighborhoods: boolean },
  // Flattened EngineMarket projection (unchanged field names) for the existing landing:
  medianPrice, ppsf, ppsfTrendPct, medianDom, monthsOfInventory, soldCount, activeCount, trend, note,
  sold_to_list?, pct_over_ask?, cut_share?, heat?
}

ENDPOINTS (additive, read-only, served from market_reports.parquet via the warm-worker-then-spawn-fallback posture of engineMarkets in src/lib/cma/engine.ts; touch no existing engine output):
- GET /api/compbird/market/[level]/[...geoId]  -> one MarketReading (the reading for a state/county/city/neighborhood).
- GET /api/compbird/market/[level]?parent=<geoId> -> MarketReading[] children (states->counties->cities->neighborhoods), for drill-down lists and generateStaticParams.
- Existing GET /api/compbird/markets stays as-is (landing cards) but is re-backed by the neighborhood rows of the same parquet.
```

## Risks
- Fabricated-coverage risk: the pool contains real out-of-state (NC/WV) and 'Out of Area' counties plus 65 nulls; without the explicit denylist these would mint bogus /va/... pages. Must hard-filter at build time.
- Junk-subdivision risk: subdivision='None' (string) is ~45% of MLS subdivision rows and 'Other' ~13%; a naive group-by creates a giant fake 'None' neighborhood. The junk filter is mandatory before any neighborhood aggregation ships.
- Heat-metric mirage: sold-to-list/over-ask/DOM/MOI are 0-populated in supplemental; showing them statewide (even as zeros) would be misleading. They must be gated to MLS-covered geos and absent elsewhere.
- Slug collision: reusing _norm_county for URLs collapses Roanoke City into Roanoke County and mangles multi-word names; a wrong slug scheme is expensive to change after pages are indexed. Lock the new normalizer + crosswalk before generating static params.
- Thin-page SEO dilution: mass-generating near-empty city/neighborhood pages can hurt SEO (thin-content penalty) and utilization. Gate at the sample floors and roll thin cities up into county pages rather than publishing empties.
- Freshness desync: never run the nightly build_market_reports while the engine server is mid-render (known Prisma/worker desync pattern); schedule it as its own task after the MLS refresh and have the endpoint read the last good parquet atomically.
- City->county ambiguity: raw city field scatters a town across up to 16 counties; resolving to the dominant county can misplace edge towns. Use parcel_lookup 'Town Of ...' jurisdiction where present and accept a small manual-override list.

## Appendix: analyst findings

### DATA FEASIBILITY
Two pools back the market section and they are asymmetric. The supplemental_listings.parquet (333,598 recorded off-MLS sales; 88,321 closed in trailing 12mo) gives statewide breadth but carries ONLY sold_price/sqft — no list_price, no DOM, no original_list_price, and NO subdivision. The mls_lookup.parquet has the rich fields (list/original-list/DOM/subdivision/active status) but is tiny (7,393 total closed; only 2,355 closed in trailing 12mo) and geographically confined to the NRV/SW-VA core (Montgomery 16.5k of 44k rows). Consequence per level: STATE (VA 85,783 + DC 4,893 closed/12mo) and COUNTY are richly supported off supplemental (129 of 138 counties clear >=25 sales/12mo). CITY/TOWN is supported for value/ppsf but thins fast (497 of 844 cities >=10, 354 >=25, only 246 >=50). NEIGHBORHOOD (subdivision) barely works: after excluding literal-string junk ("None"=1094, "Other"=186), only 1,075 MLS closed sales carry a real subdivision, yielding just 16 (county,subdivision) pairs >=10 sales/12mo and 55 >=5 — essentially all Montgomery/NRV. Critically, all "heat" metrics (sold-to-list, over-ask %, price-cut share, DOM, MOI/active inventory) are computable ONLY on the MLS pool, i.e. only for ~12 SW-VA counties, NOT statewide.
- **County-level closed sales are richly supported statewide off the supplemental pool.** — Combined trailing-12mo closed = 90,676 across 138 distinct counties. Counties clearing thresholds: >=25 sales -> 129, >=50 -> 123, >=100 -> 108. Supplemental supplies 88,321 of the 90,676 (MLS only 2,355). → *County is the safe primary geography for Phase 1: sale-price medians, YoY, and $/sqft can honestly ship for ~123-129 of ~133 VA jurisdictions plus DC.*
- **City/town level works for value metrics but the credible set shrinks quickly.** — 844 distinct cities in closed-12mo; >=10 sales -> 497, >=25 -> 354, >=50 -> 246, >=100 -> 144. Top cities are dense (Washington 4,913; Richmond 3,347; Alexandria 3,296). → *City pages should gate at >=25 sales/12mo (~354 cities ship) for medians, and reserve $/sqft trend charts for the ~246 cities >=50; below that show sale-count only or roll up to county.*
- **Neighborhood (subdivision) genuinely works only in the NRV/Roanoke core; elsewhere it is too thin to ship.** — Subdivision exists ONLY in MLS pool (708 distinct; supplemental subd count = 0). After removing junk strings, real subdivision-tagged closed sales = 1,075. County-scoped pairs: >=5 sales -> 55, >=10 -> 16, >=15 -> 7, >=25 -> 3. Of the 16 pairs >=10, Montgomery has 12; Pulaski/Roanoke/Wythe/Radford supply the rest. → *Neighborhood is NOT a statewide Phase 1 feature. Ship it only as a curated ~16-55 named-neighborhood set in SW-VA, or defer entirely; a programmatic /[state]/[city]/[neighborhood] route would be empty for 99% of VA.*
- **Subdivision field carries literal-string junk that will silently inflate/corrupt any naive grouping.** — In MLS closed-12mo, subdivision='None' (the string, not NULL) appears 1,094 times and 'Other' 186 times, together ~54% of the 2,355 subdivision-bearing rows. → *Any neighborhood aggregation MUST filter subdivision NOT IN ('None','Other','N/A','Unknown','') AND non-null; skipping this creates a bogus giant 'None' neighborhood.*
- **Heat/velocity metrics (sold-to-list, over-ask %, price-cut share, DOM) are NOT computable statewide.** — Supplemental closed-12mo (88,321 rows): list_price present=0, original_list_price=0, feed_dom=0, sold-and-list-both=0, price-cut-computable=0. MLS closed-12mo (2,355): all present, price-cut computable on 700. → *The existing market-card metrics (sold_to_list, pct_over_ask, cut_share, heat) from build_markets.py can ONLY be shown for the ~12 MLS-covered SW-VA counties. County/city pages statewide must fall back to price/ppsf/count/YoY only, with heat behind a coverage flag.*
- **Active-listing inventory (for MOI / heat / active over-ask) is confined to ~12 SW-VA counties.** — Active listings exist only in MLS pool: 912 active total, 357 pending. By county Montgomery 320, Pulaski 170, Giles 81, Floyd 79, Wythe 66; only 12 counties have >=10 active and only 7 have >=20. → *Months-of-inventory and any live supply/demand gauge cannot be a statewide feature; scope it to the SW-VA MLS footprint or omit from national/statewide pages.*
- **County and city name fields are clean; no 'Blacksburg County' bug present in current data.** — Supplemental county = proper VA independent-city + county names (Fairfax 27,920; Virginia Beach 14,582; 'District of Columbia' 14,523 = the DC state marker), 130 distinct, 0 nulls. MLS county uses '(City)' suffix (Radford (City), Roanoke (City)); zero rows matched lower(county) LIKE '%blacksburg%'/'%christiansburg%'. City null/blank in combined closed = 1. → *Grouping keys are trustworthy as-is; DC is separable at state level via county='District of Columbia'. No major cleanup blocker for county/city — the cleanliness problem is isolated to subdivision.*
- **$/sqft is broadly computable; sqft is well-populated across the combined closed pool.** — Of 90,676 closed-12mo, 86,616 (95.5%) have usable sqft>200 AND sold_price>1000. → *Median $/sqft is a safe headline metric at state/county/city levels; it does not need to be gated separately from median price.*
- **The obvious neighborhood-expansion path (enrich supplemental with parcel subdivisions) is blocked by an ID mismatch and needs a spatial join.** — parcel_lookup has subd_name on 2,307,456 of 3,444,901 parcels (67% non-junk). Supplemental has parcel_id on 100% of rows, but a direct parcel_id join yields 0 matches: supplemental parcel_id is a synthetic surrogate ('S79070321') while parcel_lookup uses real APNs ('031146'). Supplemental DOES have 100% lat/lng (333,598/333,598). → *Neighborhood coverage CAN eventually be expanded statewide, but only via a lat/lng->parcel spatial join (a real engineering lift), not a cheap key join. This is the highest-leverage data investment if neighborhood pages are a priority.*
- **Historical monthly $/sqft trend (for trend charts) exists but only for a minority of counties.** — market_index.parquet = 518 rows, 33 distinct counties, months 2023-05..2026-07. Month-depth is skewed: only ~10 counties have >=24 months of history; 9 counties have a single month. → *Multi-month trend charts should be reserved for the ~10-15 counties with >=24 months in market_index; other counties get a single-point or trailing-window figure. build_markets/market_index can be rebuilt from supplemental to widen this, since supplemental spans 2023-06..2026-06.*

### Geography Taxonomy + Slugs
The data supports a four-level hierarchy (STATE -> COUNTY/independent-city -> CITY/TOWN -> NEIGHBORHOOD) but only unevenly: county-level readings are credible statewide (parcel_lookup covers 86 VA jurisdictions across 3.44M parcels; supplemental adds sold prices for 130 counties incl. District of Columbia), while neighborhood-level readings are only credible in the MLS-covered southwest VA footprint. Neighborhood must be defined as the MLS `subdivision` field, NOT a lat/lng cluster, for the primary path — but subdivision is only usefully populated in ~13 New River Valley counties, its top two values are the literal strings "None" (45% of rows) and "Other" (13%), and only ~123 named subdivisions have >=8 sold comps. There is NO `state` column anywhere; state must be derived (default VA; DC only via county="District of Columbia"; and the pool contains ~10 out-of-state NC/WV counties that must be filtered, not published). City->county is genuinely many-to-many and the raw `city` field is data-entry-noisy ("Radford" appears across 16 counties), so a city page must be scoped under a county, never stand alone. The existing `_norm_county` normalizer is correct for CMA matching but WRONG as a slug generator — it collapses independent cities into counties (Roanoke City == Roanoke County -> "roanoke") and mangles multi-word names (James City County -> "james", Isle of Wight County -> "isle wight"), so slugs need a new dedicated normalizer plus a small hand-maintained crosswalk. Every published geography must be gated on a real sample-size floor with a "never fabricate a county/name" rule enforced against a canonical jurisdiction list derived from parcel_lookup.
- **There is no state column in any parquet; state must be derived, and the pool contains real out-of-state noise that would fabricate coverage if published.** — mls_lookup.parquet has no state field (51 columns, none is state). County values include WV (Monroe 468, Mercer 45, Summers 63, Greenbrier 6) and NC (Stokes 161, Forsyth 15, Rockingham - NC 11, Surry 78, Yadkin 6, Wilkes 4), plus 'Out of Area' (11) and 65 nulls. DC surfaces only as county='District of Columbia' (14,523 rows in supplemental_listings.parquet). → *State is a derived attribute: default VA, DC iff county='District of Columbia', and an explicit allowlist/filter must drop NC/WV/'Out of Area'/null before any /va/... or /dc/... page is generated. Publish exactly two state roots: /va and /dc.*
- **County (with independent-city variants) is the only geography level credibly readable statewide, and parcel_lookup.jurisdiction is the authoritative canonical crosswalk.** — parcel_lookup.parquet = 3,444,901 rows across 86 distinct jurisdictions spanning all of VA (Fairfax County 370k, Virginia Beach City 157k, ... Radford 5,306). supplemental_listings adds sold prices for 130 counties. But the MLS Closed-sold pool is thin outside the New River Valley: only Montgomery (3,262 sold), Pulaski (1,388), Giles (524), Floyd (503), Radford City (483) exceed a few hundred; most VA counties have zero MLS solds and rely on supplemental only. → *Every VA county/independent-city gets a page, but the metric set must degrade by data regime: MLS-rich counties get full heat/DOM/cut stats; supplemental-only counties get sold-price/$psf trends and an honest 'limited coverage' state. Build the canonical county list FROM parcel_lookup.jurisdiction (normalized), not from the noisy MLS county field.*
- **The existing _norm_county normalizer is unsafe as a slug generator — it collapses distinct jurisdictions and mangles multi-word names.** — cma_regions._norm_county strips the words county/city/co/of and all non-[a-z ] chars: 'Roanoke County' and 'Roanoke City' both -> 'roanoke'; 'James City County' -> 'james'; 'Isle of Wight County' -> 'isle wight'; 'Radford (City)' -> 'radford'; 'Galax (City)' -> 'galax'. market_index.parquet.county_norm inherits this (Radford City folded into 'radford'). → *Slugs need a NEW dedicated normalizer that (a) preserves the county-vs-independent-city distinction (e.g. roanoke-county vs roanoke-city, and radford as its own independent-city node), (b) never deletes interior words, only lowercases + hyphenates + strips the trailing 'County'/'City' descriptor into a controlled suffix. Keep _norm_county for engine/CMA matching; do not reuse it for URLs.*
- **Neighborhood must be the MLS subdivision field, but it is sparse, placeholder-polluted, and effectively absent outside SW VA / entirely absent in DC.** — subdivision is ~95% non-null in the top counties but the top two values are literal 'None' (19,732 rows = 45%) and 'Other' (5,558 = 13%); real named coverage is only 16,172/44,084 = 37%. 706 distinct real subdivisions exist but only 123 have >=8 Closed sales and 57 have >=15. supplemental_listings.subdivision is 100% NULL (0/333,598), and DC has 0 distinct subdivisions. build_markets.py already treats ('','NONE','OTHER','N/A','NA','UNKNOWN','TBD') as placeholders. → *Neighborhood pages exist ONLY where the MLS pool covers (the ~13 NRV counties) AND a named subdivision clears a sold-count floor (recommend >=8 trailing sold). Reuse the existing PLACEHOLDERS set. For DC and statewide supplemental-only areas there is NO neighborhood tier from this data — do not fabricate one. A lat/lng geo-cluster is the only theoretical fallback (lat/lng is 100% populated in both sources) but should be deferred/labeled synthetic, not the v1 definition.*
- **City->county is many-to-many and the raw city field is noisy, so a city can never be a standalone slug parent — it must nest under a county.** — 'Radford' (the independent-city name) appears attached to 16 different counties (4,086 rows), 'Hillsville' to 4, 'Roanoke' to 4, 'Floyd' to 3, 'Christiansburg' to 2 (Montgomery + a stray Monroe). This is data-entry noise: the town genuinely sits in one county but the feed scatters it. supplemental has 1,034 distinct city values including DC variants 'Washington','WASHINGTON','Northwest Washington','Fort washington' (casing + directional-quadrant noise). → *City/town pages must be keyed by (county_slug, city_slug) and resolved to the DOMINANT county (mode of listings, or the parcel_lookup 'Town Of ...'/city jurisdiction when present). URL = /va/<county>-county/<city>. Do casing/whitespace canonicalization and fold DC directional variants. A bare /va/<city> slug is unsafe and must not be minted.*
- **Slug scheme should be explicit-descriptor, hyphenated, apostrophe-stripped, and disambiguated at the county tier; the goal's example already validates against real data.** — Real values needing normalization: "Fiddler's Green" (n=89, apostrophe), 'Meadows Of Dan' (mixed case), "Hogan's Retreat", "The Village at Tom's Creek", 'A D Akers Addition'. parcel_lookup jurisdiction formats are inconsistent ('Roanoke City' vs 'Roanoke County' vs ALL-CAPS bare 'BEDFORD'/'MONTGOMERY'/'BLACKSBURG'/'CHRISTIANSBURG' vs 'Town Of Vinton'). → *Slug rules: lowercase; strip apostrophes/periods; non-alnum -> single hyphen; collapse repeats; trim. Append a controlled descriptor to disambiguate the independent-city-vs-county collision: /va/montgomery-county, /va/roanoke-county, /va/roanoke-city, /va/radford (independent city). Example resolves cleanly: /va/montgomery-county/blacksburg/fiddlers-green. Store a slug<->canonical-display map so display stays 'Fiddler's Green, Blacksburg, Montgomery County, VA'.*
- **A small hand-maintained crosswalk is needed on top of the derivable pool; most of the taxonomy is derivable but the ambiguous edges are not.** — Derivable from data: county universe (parcel_lookup.jurisdiction, 86 values), county<->city membership (mode over pool), named subdivisions + their county/city (build_markets already does ANY_VALUE(city)/ANY_VALUE(county) per subdivision). ### Engine Aggregation Design — market-reading metrics per geography level
The market-reading system must be built on TWO complementary pools whose coverage dictates which metrics exist at each level — this is the single most important design fact, and I verified it with real counts. data/mls_lookup.parquet is an hourly New-River-Valley-only pool (~2,001 closed RE_1 sales/12mo across 30 counties, but only Montgomery/Pulaski/Giles/Radford/Wythe/Floyd have >=100) that is the ONLY source with list_price, original_list_price, feed_dom, and Active/Pending rows — so it alone yields DOM quantiles, sold-to-list, %-over-ask, cut-share, and months-of-inventory. data/supplemental_listings.parquet is statewide (130 VA+DC counties, ALL >=25 sold/24mo, 126 >=100; 511 cities >=25) with sold_price + sqft but NO list price, NO DOM, NO active listings, and 100% NULL subdivision AND property_subtype — so statewide it yields only median price, median $/sqft + YoY, price distribution, and sold count. Consequently the CANONICAL design is a nightly-precomputed market_reports.parquet keyed by (level, geo_id), where each metric carries its own availability flag: STATE and COUNTY levels blend both pools (price/$/sqft/distribution statewide from supplemental, DOM/MOI/sold-to-list/heat from MLS where the county is in NRV), CITY is price+$/sqft statewide but full-metric only in NRV, and NEIGHBORHOOD (subdivision) is NRV-only because supplemental has zero subdivision data. A single-pass DuckDB all-county aggregate ran in 0.01s, so nightly precompute is trivially cheap and there is no reason to compute on-demand in the warm worker; the existing build_markets.py neighborhood cards become the neighborhood tier of the same parquet, unchanged in shape. All of this is additive/compbird-only and touches no existing Ratifyly engine output.
- **Two pools with disjoint metric coverage — the whole design pivots on this. mls_lookup is NRV-only but metric-rich; supplemental is statewide but metric-thin.** — Real counts: mls_lookup closed RE_1 12mo = 2,001 sales, 30 counties, only Montgomery(904)/Pulaski(404)/Giles(152)/Radford(127)/Wythe(108)/Floyd(102) are >=100. supplemental = 333,598 rows, 130 counties ALL >=25 sold/24mo (126 >=100), spanning Fairfax(18,474) to DC(9,748). supplemental list_price>0 rows = 0, feed_dom notnull = 0, Active = 0. → *DOM, sold-to-list, %-over-ask, cut-share, months-of-inventory, and heat CANNOT be computed statewide — only for NRV counties/cities/subdivisions from mls_lookup. Median price, median $/sqft, YoY, distribution, sold count are computable statewide from supplemental. The MarketReading JSON must gate each metric with an availability flag, not assume all fields exist at every level.*
- **Neighborhood level is MLS-pool-only. supplemental has NO subdivision data at all, so the deepest geography (subdivision) exists only where mls_lookup has coverage (NRV today).** — supplemental subdivision NULL/placeholder = 199,223 of 199,223 (100%) in the 24mo window; distinct real subdivisions statewide = 0. mls_lookup by contrast has 339 real subdivisions in NRV, 37 with >=6 sold, 13 with >=10 (build_markets.py already surfaces the top 6 as landing cards). → *The NEIGHBORHOOD tier of the browsable system is credibly buildable ONLY for NRV. build_markets.py (scripts/build_markets.py, MIN_SOLD=6, real-name placeholder filter) is already exactly this — it becomes the neighborhood rows of market_reports.parquet verbatim. Outside NRV the drill-down must stop at CITY until MLS coverage or parcel-derived neighborhoods expand; the app should hide the neighborhood tier when geo has none rather than show empty cards.*
- **Nightly precompute into market_reports.parquet is the right architecture (not on-demand): the full aggregate is essentially free and the pool is hourly, so a nightly job is fresh enough.** — A single-pass DuckDB GROUP BY county over all 130 counties (median price + median $/sqft + count, 12mo window) completed in 0.01s measured. The existing per-neighborhood build_markets.py path is budgeted at 18s (MARKETS_WORKER_MS/MARKETS_SPAWN_MS in engine.ts:48-52) because it does N sequential per-subdivision scans; a keyed precompute eliminates that. → *Build market_reports.parquet in a nightly task (mirror tasks.py mls-rebuild-market-index at scripts/build_market_index.py) after the hourly MLS refresh. The warm worker/app just reads keyed rows — one cheap indexed lookup per page, no live DuckDB scan, no 18s budget, no per-request coalescing needed. Freshness = nightly is fine since county/city aggregates move slowly; the hourly pool feeds the next nightly build.*
- **Every headline metric was verified computable with the exact SQL patterns already in the codebase — reuse, don't reinvent.** — Median $/sqft YoY from supplemental: Fairfax recent 464.2 vs prior 461.2 = +0.7% on n_recent=8,851 (split-window MEDIAN, same idea as build_markets.py:206-229 split-half trend). DOM quantiles from mls_lookup via QUANTILE_CONT: Montgomery q25/q50/q75 = 3/14/49 (same model family as build_cma.py _dom_pricing_band:1894). Price distribution via FLOOR(sold_price/100000) bucketing: Fairfax 12mo gives a clean 16-bucket histogram (0->1,086 in $1.5M+). $/sqft trend series and MOI already in build_markets.py; county $/sqft index (48mo smoothed) already in market_index.parquet (518 rows, 33 counties, 15 YoY-capable). → *MarketReading metrics map 1:1 to existing patterns: median price/$/sqft/DOM/MOI/sold-to-list/%-over-ask/cut-share/heat from build_markets.py; $/sqft YoY + trend sparkline from market_index.py index_ratio (county level) or split-window (city/neighborhood); DOM quantiles from QUANTILE_CONT; distribution from FLOOR bucketing. No new math — just re-scope GROUP BY from subdivision to (level, geo_id).*
- **property_subtype (type mix) is available from the MLS pool but NULL in supplemental — so type-mix is an NRV-only enrichment, same coverage class as DOM.** — supplemental property_subtype = 100% NULL (199,223/199,223). mls_lookup property_subtype closed RE_1 12mo: Detached 1,710, Townhouse 204, Condominium 87 — clean and populated. → *Treat propertyTypeMix as an optional MLS-only metric with the same availability gate as DOM/heat: present for NRV county/city/neighborhood, absent statewide. Do not promise type mix on the statewide county/city pages.*
- **Sample-gating thresholds should be per-metric and per-level, driven by the measured distributions, and the JSON must carry sample sizes so the app can render 'thin data' states.** — Measured credible-sample cutoffs: counties with >=100 sold = 6 (mls) / 126 (supp); cities >=25 = 12 (mls NRV) / 511 (supp statewide); subdivisions >=6 = 37, >=10 = 13 (mls). market_index.py already uses MIN_SALES=8 for its index ratio and build_markets.py uses MIN_SOLD=6 for a card. → *Adopt tiered minimums: STATE always (huge n), COUNTY needs >=25 sold for price/$/sqft (>=50 for distribution), CITY >=15 sold, NEIGHBORHOOD >=6 (reuse build_markets MIN_SOLD). Each metric object should include n (sample) and a boolean available; YoY needs both windows populated (reuse market_index.py's degrade-to-None when a month has n_sales<8). The app omits/greys any metric whose n is below its floor rather than showing a noisy figure.*
- **The consuming JSON should be a single MarketReading object per (level, geo_id), a superset of today's EngineMarket, so the existing /markets landing cards and the new browsable pages share one shape.** — Today's contract: engine.ts EngineMarket (engine.ts:562-584) = {name, area, medianPrice, ppsf, ppsfTrendPct, medianDom, monthsOfInventory, soldCount, activeCount, trend[], note, optional sold_to_list/pct_over_ask/cut_share/heat}. Route = src/app/api/compbird/markets/route.ts (GET, no params). No /markets route or [state]/[county] pages exist yet. → *Define MarketReading = { level: 'state'|'county'|'city'|'neighborhood', geoId, name, area, state, parent, generatedAt, sold: {n, medianPrice, medianPpsf, ppsfYoyPct, ppsfTrend[], distribution: {bucketLo,count}[] }, velocity?: {medianDom, domQuantiles:{q25,q50,q75}, monthsOfInventory, activeCount, soldToList, pctOverAsk, cutShare, heat}, typeMix?: {label,count}[], available: {velocity: bool, typeMix: bool, neighborhoods: bool} }. Keep the exact EngineMarket field names as a flattened projection so the current landing keeps working. Add endpoints: GET /api/compbird/market/[level]/[geoId] (one reading) and GET /api/compbird/market/[level]?parent= (children list, e.g. counties in a state, cities in a county) — both served from market_reports.parquet via the warm worker, additive to the engine, zero change to Ratifyly outputs.*
